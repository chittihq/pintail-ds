# pintail-ds

Versioned, reproducible benchmark datasets for [pintail](https://github.com/chittihq/pintail).

This repository is the **index and provenance layer**: manifests, checksums, and fetch
scripts live in git; small dataset tiers (smoke, ci) are stored directly as files; large
tiers (full) are distributed as chunked GitHub Release assets referenced by the manifest
(additional mirrors, e.g. R2, can be added to `urls` without changing consumers).

## Layout

```
datasets/<workload>/<dataset-hash>/
├── manifest.json          # tables, row counts, sha256 per file, mirror URLs, provenance
└── data/                  # smoke/ci tiers only: <table>.tsv.zst committed in-repo
```

`dataset-hash` = sha256 over (workload id, seed, scale, production-profile.json, seeder
version). Identical inputs always reproduce byte-identical data — any manifest can be
regenerated and verified from the pinned pintail commit.

## Consuming

```bash
bun scripts/fetch.ts commerce-production-v1 <dataset-hash-or-alias> ./cache
# verifies sha256 of every file; exits nonzero on any mismatch
```

Aliases: `datasets/<workload>/aliases.json` maps `smoke` / `ci` / `full` to the current
dataset hash. `benchmark/run-production.ts` in the pintail repo resolves datasets through
this mechanism automatically when `--dataset` is passed.

## Publishing (maintainers)

Datasets are generated by the pintail repo's deterministic seeder and exported with
`mysqldump --tab` (server-side TSV), compressed with zstd, hashed, and committed here by
`benchmark/publish-dataset.ts` in the pintail repo. Full-scale artifacts are uploaded as
release assets (`gh release create ds-<workload>-<hash>`), chunked below 2 GB.

## Format

- One `<table>.tsv.zst` per table: MySQL `mysqldump --tab` TSV (tab-separated, `\N` for
  NULL, MySQL escaping), zstd-compressed.
- Loaded with `LOAD DATA INFILE` after decompression; secondary indexes are created after
  load by the consumer.
